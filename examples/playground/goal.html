The security model

Treat every upload
as hostile bytes.

An image file is not what its extension or MIME type claims. It is bytes that a decoder will execute—parsers with CVE histories, containers that understate their dimensions, and metadata that can leak more than users intended.

01 · routes

Three outcomes.
No hidden path.

Optload makes the decision explicit. The browser improves the experience; the server remains the authority.

Local

Inspect a bounded prefix, enforce policy, and normalize supported still images in one fresh worker. Return a smaller blob with the source structure removed.

Server fallback

Missing a codec, dimension, or isolated-worker capability? Pass the original file, the inspection, and the reason to your configured server route.

Reject

Active content, animation, decompression-bomb dimensions, or another policy violation stops before a decoder runs.

02 · authority

Fast on the client.
Verified at the edge.

Browser output is still untrusted input. Client-side normalization improves latency, bandwidth, and privacy, but the receiving server must re-inspect the bytes, decode outside the application process, re-encode, and verify the result before storage or serving.

The reference Sharp adapter uses one child process per image and a buffer-loader allowlist. Containerize the service or use an external sandbox when the deployment threat model requires stronger resource, filesystem, syscall, or egress controls.

03 · defaults

A safer route
starts before decode.

Bounded inspection

Headers are read from a capped prefix. Filenames and declared MIME types are reported, never trusted.

Fresh isolation

Each browser image gets a fresh worker. Each server image gets a declared process or service boundary.

Typed decisions

Local, fallback, and reject are successful or typed failure results your code can handle directly.
